================================================================================
 HYPERLOCAL PRODUCT DISCOVERY PLATFORM
 FINAL DATABASE SCHEMA DESIGN   (Master Specification Phase 2 / §10-§29, §52)
================================================================================

DOCUMENT PURPOSE
--------------------------------------------------------------------------------
This is the canonical database architecture for the hyperlocal product
discovery platform. For every domain it defines the entities, columns,
primary/foreign keys, unique & check constraints, indexes and the PostGIS
strategy, and maps each entity to the Alembic migration that materialises it.

It implements the Master Specification rules verbatim:
 RULE 1 Product Master != Inventory
 RULE 2 Inventory != Price
 RULE 3 Price != Offer
 RULE 4 Restaurant != Normal Product Shop
 RULE 5 Transport != Product Inventory
 RULE 6 Personal Transport Booking != Product Order
 RULE 9 Search Engine != Primary Database
 RULE 13 Grocery / general food retail is OUT OF SCOPE

STATUS LEGEND
--------------------------------------------------------------------------------
  [C] Committed   - exists in the committed Alembic chain (0001-0013).
  [W] In-progress - authored but NOT yet committed (migration 0014 + models).
  [P] Proposed    - designed in this document for a coming phase; exact DDL
 will follow in the next migration. Never confuse with [C]/[W].

STACK & GLOBAL CONVENTIONS
--------------------------------------------------------------------------------
DB        : PostgreSQL 16 + PostGIS 3.4 (extensions: postgis, pg_trgm).
Geometry  : GeoAlchemy2 Geography(type, srid=4326) for great-circle distances;
 a GiST index exists on every geography column.
IDs       : SERIAL/INTEGER surrogate PKs; natural keys are UNIQUE constraints.
Money     : NUMERIC(12,2); every money column carries CHECK (>= 0).
Quantity  : INTEGER; CHECK (>= 0)  - negative stock is structurally impossible.
Enums     : Stable domain enums use native PostgreSQL ENUM (user_status,
 stock_status, shop_category, etc.). Volatile/rapidly-evolving enums
 use VARCHAR + CHECK so ALTER TYPE lock pain is avoided. New tables
 should default to VARCHAR + CHECK (project pattern since 0012).
Timestamps: EVERY table has created_at + updated_at TIMESTAMPTZ NOT NULL
 DEFAULT now(); updated_at gets ON UPDATE now() (TimestampMixin).
SoftDelete: Entities with legal/compliance lifecycles carry is_deleted BOOLEAN
 NOT NULL DEFAULT false + deleted_at TIMESTAMPTZ (SoftDeleteMixin).
 Hard delete is reserved for logs / append-only streams.
Audit     : created_by / updated_by INTEGER on business tables where an actor
 is meaningful; high-risk transitions also append a row to
 audit_logs (tamper-evident hash chain over record_hash).
Search    : search_indexes is a denormalised, rebuildable projection served by
 the SearchIndexer. PostgreSQL remains the authoritative store.
Cache     : Redis holds cache, production OTP state, rate-limit counters and
 the Celery broker/result store. Redis is NEVER the source of truth.

================================================================================
 DATA CONSISTENCY RULES (enforced by CHECK / UNIQUE / FK constraints)
================================================================================
   1. quantity >= 0 in inventory.               (ck_inventory_quantity_non_negative)
  2. price / mrp >= 0 everywhere money appears.  (ck on shop_products, price_history)
   3. rating IN [0, 5]and review_count >= 0 on shops; rating IN [1, 5] on
 user_interactions (and proposed reviews.
   4. offer end_date > start_date.                   (ck_offers_end_after_start)
   5. one product master NEVER duplicated: UQ categories.slug, brands.slug,
 product_masters.slug, product_identifiers(identifier_type,value) etc.
   6. one shop-product link: UQ shop_products(shop_id, product_master_id, variant_id)
 plus UQ(shop_id, sku).
   7. one inventory row per shop-product.             (uq_inventory_shop_product)
   8. one favourite per (customer,item): uq_customer_favorite_customer_item.

   9. one active subscription per (user|shop): enforced at the service layer;
 payments reference the subscription and provider (order_id/transaction_id) are UQ.
  10. OTP/reset tokens: single-use(, expiring(, flips is_verified/is_used).
  11. bookings (proposed) are never FK'd to shop_products/inventory.
  12. RBAC: users.role_id + user_roles M2M; permissions via role_permissions.-
  13. Unique service-area name; area_type CHECK IN CITY/ZONE/LOCALITY/PINCODE.-

 INDEXING & PERFORMANCE (hot paths from Master Spec §46)
================================================================================
 Hot path 1 - "search any product near me":
 search_indexes: GIN(search_vector), GIN(search_text gin_trgm_ops),
 GIN(barcode gin_trgm_ops) for typo-tolerant full-text;

 shop_products(shop_id,variant_id), shop_products(shop_id,is_available),
 inventory(shop_product_id) UNIQUE.          (Added in 0014.)
 3. nearby shop: shops(location) GiST; shop_addresses(location) GiST.
 4. service zones: service_areas(boundary) GiST, (center) GiST, pincode_prefix,
 partial(active) index.                              (Added in 0014.)
  5. auth: users(phone_number|google_id) UQ; auth_sessions(user_id,is_active),
 refresh_token_hash; token_blacklist(jti) UQ.
  6. product detail / shop detail: PK lookups; composite (name,brand_id) etc./
 7. analytics: analytics_events(event_name,occurred_at), (actor_type,occurred_at),
     (shop_id,occurred_at), (product_master_id,occurred_at); daily rollup for reports.

 Rules: measure first; prefer composite over many single-column indexes; use partial
 indexes for hot-but-sparse predicates; GiST only on geography/geometry columns;
 every business-unique key MUST carry an index (Postgres auto-indexes UQ).

================================================================================
 CLOSING NOTE
================================================================================
 This design freezes the Phase-2 canonical database for the platform: every
 entity the Master Specification requires is either [C] implemented (with its
 exact Alembic migration), [W] in-progress (0014), or [P] designed with exact
 columns here for the next migration after the current work lands. The three
 irreducible invariants of the whole scheme are:
    1. product identity (product_masters) is global and ONE per product.
    2. price/stock/availability are shop-specific (shop_products/inventory/price
        _history).
    3. services (restaurants, transport) live in their own domains, never
 blended into product inventory; transport bookings are their own
 aggregates, never product orders.
